# Сценарий демонстрации продукта

Демо рассчитано на 6 минут. Порядок жёсткий, чтобы не путаться: от простого к
сложному, каждое действие сопровождается коротким пояснением.

## Подготовка (до защиты)

```bash
python run.py
# приложение доступно по адресу http://127.0.0.1:5000
```

Учётные записи: `admin` / `admin123` (администратор), `demo` / `demo123` (клиент).
База наполнена тестовыми данными: 5 фильмов, 6 сеансов.

## План демонстрации

| Время | Действие | Что говорится |
|---|---|---|
| 0:00–0:30 | запуск `python run.py`, открытие `http://127.0.0.1:5000` | приложение локальное, база SQLite наполнена тестовыми данными |
| 0:30–1:10 | афиша, выбор фильма «Путь к звёздам» | афиша показывает ближайшие сеансы, вход для просмотра не нужен |
| 1:10–1:50 | вход `demo` / `demo123` | роль клиента берётся из таблицы `users`, пароль хранится SHA-256-хешем |
| 1:50–2:40 | схема зала 5 × 10, бронирование места 3-7 | занятые места видны сразу, ограничение `UNIQUE` не даёт продать место дважды |
| 2:40–3:10 | повторная попытка занять место 3-5 | сообщение «Место уже занято», схема обновляется — обработка альтернативного потока |
| 3:10–3:40 | «Мои билеты», отмена брони | билет со статусом `booked` становится `canceled`, место освобождается |
| 3:40–4:30 | выход, вход `admin` / `admin123`, админ-панель | сводка: 4 фильма, 6 сеансов, 3 действующих билета, выручка 1020 ₽ |
| 4:30–5:20 | добавление фильма, редактирование, удаление | CRUD афиши без программиста; удаление фильма с сеансами запрещено |
| 5:20–6:00 | отчёт о продажах, возврат к афише | выручка и число билетов совпадают с данными в базе |

## Ответы на вероятные вопросы комиссии

**«Почему Flask и SQLite?»** Flask выбран потому, что проект учебный и
небольшой: фреймворк не навязывает структуру, поэтому видно, как устроены
маршруты, сессии и шаблоны, а не как работает «магия» фреймворка. Flask
устанавливается одной командой, не требует отдельного сервера приложений и
запускается на слабом ноутбуке. SQLite не требует установки и
администрирования, хранит базу в одном файле `project.db`, поддерживает
транзакции, внешние ключи и ограничение `UNIQUE`, чего достаточно для зала на
50 мест. Для промышленной нагрузки SQLite не подошёл бы из-за блокировок на
запись.

**«Как обеспечили качество и безопасность?»** Качество подтверждено
измеримыми показателями: 33 автотеста pytest, покрытие ветвей 86 %, замечаний
линтера flake8 нет, средняя цикломатическая сложность 2,33 при максимуме 6.
Безопасность обеспечена разграничением ролей через декораторы
`login_required` и `admin_required`, хешированием паролей SHA-256, проверкой
всех форм на сервере, защитой от open redirect (функция `_safe_next_url`),
понятными страницами ошибок 403, 404 и 500 с записью сбоев в `app.log`.

**«Что бы улучшили, если было бы больше времени?»** В плане развития
зафиксированы четыре пункта: CSRF-защита форм (сейчас не подключён
Flask-WTF), соль к хешам паролей, проверка даты сеанса при бронировании
(сейчас можно забронировать место на прошедший сеанс) и подключение
платёжного шлюза. Кроме того, планируется добавить тесты на редактирование
фильма с несуществующим идентификатором и расширить отчётность — выручку по
периодам и залам.

## План Б, если демо не запускается

1. Показать заранее сделанные скриншоты из `docs/screenshots/` — в репозитории
   их 15, включая все ключевые экраны и сообщения об ошибках.
2. Открыть презентацию `docs/Презентация продукта.pdf`.
3. Показать пошаговую инструкцию запуска в `README.md` — если проблема в
   окружении, видно, что проект запускается по инструкции.
